# Backend Architecture Map

## Desktop Runtime Boundary

- The desktop app uses `codex-rs/app-server` as the Codex runtime boundary and must not create a parallel agent runtime.
- `codex-rs/app-server-protocol` defines the contract for threads, turns, streamed items, permissions, filesystem operations, config, models, account, review, plugins, apps, and MCP surfaces.
- Desktop-owned state should stay product-facing: project metadata, pinned folders, display names, ordering, hidden/archived projects, last active thread, inspector selection, panel layout, recent composer/settings choices, mockup history, and plan preview state.
- App-server-owned state remains runtime-facing: threads, turns, transcript persistence, tools, command execution, file changes, approvals, sandboxing, review events, and model/config/account reads.
- Old persisted coordinate-planning keys from pre-P20 local state are not loaded into current state. They may remain in a user's saved JSON blob, but the desktop normalizer drops them.
- Active-turn progress uses app-server streamed item events first. The desktop renderer normalizes command items, streamed file-change patches, and bounded workspace snapshots into one turn-scoped progress summary that feeds the transcript and the composer-adjacent progress/review pill. When file-change snapshots are not yet available, Electron exposes a turn-scoped `workspace_progress_snapshot` helper that reports bounded text-file path, line-count, and timestamp summaries only; it skips generated/heavy directories, binary files, large files, and lockfiles and does not persist transcript state.
- Progress summaries key files by project-relative path so relative streamed file-change paths and absolute workspace snapshot paths merge into one row. The composer-adjacent pill is visible for active turns even before file writes: it shows elapsed time, command activity, and honest "no file writes observed yet" states, then switches to changed-line totals when writes become observable. The transcript progress card uses the same summary and may render bounded 10-second observable checkpoints during long no-write spans.

## Live App Preview

- App Preview is the primary visual surface for existing runnable projects. It is available from normal chat and Plan Mode.
- P33 architecture direction: existing-project feature preview should be a Live-first draft layer. Internally, a draft may reuse isolated code-backed workspace infrastructure, preview flags, and mock data/backend conventions, but it should be presented as `Live + Draft` rather than mandatory A/B/C. The user's main working tree should remain unchanged until `Build this`.
- A user can open the app preview, run/stop/reload the project preview, draw an area mark, and continue chatting without using a mention.
- The preview host is desktop-owned UI/runtime state. It must not create a parallel agent runtime or bypass `codex-rs/app-server` for Codex work.
- The Electron host uses a controlled `<webview>` guest for project app previews. Do not regress this to parent-page overlay rendering.
- Electron enables preview lifecycle through small desktop IPC commands: probe a user-provided local HTTP URL, discover likely local preview URLs on request, reject Codex runtime/bridge ports, and return an honest availability/title result.
- Electron also owns a managed project-preview lifecycle: start, stop, and status by project path. Managed preview start chooses an available local port, starts common `package.json` apps when a runnable script exists, or serves plain `index.html` projects through a local static server. Simple `node <file>` package scripts are spawned directly instead of through the package manager wrapper so Electron can stop the actual preview server reliably. If no runnable app exists, it returns an honest baseline-needed state instead of rendering a blank backend/debug page.
- Electron exposes small desktop-owned helpers for mockup-first flows: `project_empty_status` provides factual empty-project state for the prompt wrapper, and `mockups_list` reads saved `.codex/mockups` artifacts for first-party preview. These helpers are UI workflow state, not a parallel Codex runtime and not a desktop-owned questionnaire.
- Electron's native app-server bridge is session-token gated for the desktop renderer. Preview/webview content must not be able to connect to the Codex bridge by opening the loopback websocket directly.
- Preview URL probing should validate redirected final URLs, reject Codex runtime ports, and bound response reads so a broken or hostile local server cannot turn preview detection into a slow/debuggy backend surface.
- Remember preview URLs per project. If a project has no remembered URL, do not automatically show another project's last preview; show the unavailable/choose URL state instead.
- Managed preview processes are per project and opt-in. Do not auto-start every known project. Stopping a managed preview should stop only that project's process/server and clear the active webview.
- Preview state should include project ID, URL, route label, viewport, status, error, updated timestamp, and cleanup/reset status.
- Normal-chat existing-app live-overlay proposals reuse the Plan Preview path instead of a parallel artifact system. The model returns a hidden `codex-plan-preview` block, desktop stores it as a `live_proposal` `PlanProposal`, and `LiveAppPreview` records hidden proposal metadata plus optional highlights for the existing webview.
- `PlanPreviewSpec` carries optional route, view state, target region, and per-variant proposal highlights. Highlights are rendered by Live Preview only when the user chooses `Show changes`; they are supporting review metadata, not accepted app UI.
- Plan Preview proposal lanes opt into the managed preview auto-start path so a selected `A/B/C` live-overlay proposal can show change highlights and marks immediately. Saved mockup proposal lanes are static iframe artifacts, but they still expose a stopped `Live` lane target while active, even before the project has runnable app files.
- Streamed agent text can contain hidden preview JSON that app-server completion payloads may omit. Desktop buffers streamed final-agent message text per turn and merges it into the completed turn before parsing so preview specs survive completion/list refresh.
- P25b architecture: serious new-app, new-page, redesign, and large UI proposals can use isolated code-backed proposal workspaces. Desktop owns workspace creation, baseline snapshots, diff/patch computation, preview lifecycle, and promotion checks; app-server turns still do the Codex work inside those proposal workspace paths rather than creating a parallel agent runtime. Cleanup/history polish remains future work.
- Implemented P33 Phase 1 foundation: `apps/desktop/electron/draft-workspaces.cjs` provides hidden draft workspace prepare/diff/lifecycle/brief helpers. It adapts the existing code-backed proposal workspace copy/diff/bounds machinery underneath a separate draft registry, so drafts are not represented as visible `A/B/C` proposal sets.
- A P33 draft registry tracks draft name, owning project/thread, lifecycle (`active`, `parked`, `built`, `discarded`), affected routes, hidden workspace/preview owner pointers, mock assumptions, and a draft brief path such as `.codex/drafts/<draft-slug>/brief.md`. The brief is durable product memory for the draft; the registry remains hidden implementation state.
- Implemented P33 renderer/build slice: desktop state now has `featureDrafts` plus active draft pointers by thread, `DraftPreview` reuses `LiveAppPreview` as `Live + Draft`, and `App.tsx` can route clear existing-project single-feature preview prompts into one hidden draft workspace. Draft revision stays in the workspace; explicit `Build this` uses `draft_workspace_apply`, which reuses the code-backed proposal workspace apply/conflict machinery and mutates Live only after approval. `Park`, `Resume`, and `Discard` update draft lifecycle without exposing draft workspace internals. Active or parked drafts surface in a compact above-composer strip for the owning thread, with a project-scoped fallback when an empty backing thread has not materialized in chat history yet.
- Implemented P27: live overlay proposals, saved mockups, code-backed proposal workspaces, user marks, and agent change marks now feed a derived Canvas action/state model before prompt routing. `apps/desktop/src/canvasActions.ts` owns the canonical actions (`ASK_USER`, `CREATE_PROPOSAL`, `REVISE_PROPOSAL`, `ADD_OPTION`, `BUILD_SELECTED`, `BUILD_LIVE_DIRECTLY`, `ARCHIVE_PROPOSALS`) and the reviewable Canvas operating prompt; `App.tsx` adapts existing proposal stores into that model while preserving the app-server runtime boundary.
- P27b cleanup removed the old fixed empty-project/current-app questionnaire wrappers, completed-turn fallback synthesis, and the separate `[Codex Existing App Preview First Context]` saved-preview creation sentinel. Canvas questions now use one `[Codex Canvas Question Context]` wrapper and agent-authored `codex-decision-strip` choices; saved review artifact creation uses the saved-mockup review path. Do not reintroduce `Empty Project Visual Planning`, `Existing App Visual Decision`, or existing-app-preview-first sentinel families as separate routing systems.
- Code-backed proposal lifecycle uses separate thread pointers for active routing and visible comparison. After a selected runnable proposal is built into Live, the code proposal set is marked applied, removed from active routing, and retained as a `Live | A | B | C` comparison reference so the user can verify the result without stale A/B/C catching the next ambiguous prompt.
- Implemented P27-cool architecture: `LiveAppPreview`, `MockupPreview`, and the proposal adapters render Live and proposal lanes (`A`, `B`, `C`) as distinct row-local surfaces above the existing Live, saved mockup, live overlay, and code-backed workspace stores. Desktop/Mobile viewport switching renders once as floating Canvas chrome. Active live proposals must be pending and preview-backed; accepted or no-preview proposal shells retarget to Live/compare instead of remaining selected, and a current active live proposal retargets stale saved-mockup inspector selection back to Plan Preview. Code-backed workspace paths are display-sanitized so the user sees product labels such as `Option A` or project-relative file paths, not proposal workspace folders.
- Implemented P30 proof: `apps/desktop/src/visualPatchRuntime.ts` owns a minimal preview-only `VisualPatchV0` runtime for `style` and optional `text` patches targeted by `data-canvas-id`. It generates install/apply/clear scripts for the preview renderer, reapplies active patches after target replacement, and restores the original visual state on clear. This is a foundation only; proposal registry, A/B/C backing, source conversion, and Edit Mode remain P30b/P31 work.
- Implemented P30b Phase 1: Canvas proposal display lanes (`A/B/C`) are now separate from proposal backing. `apps/desktop/src/canvasProposalModel.ts` defines backing types (`wireframe_artifact`, `mockup_artifact`, `live_dom_patch`, `code_backed_workspace`), lifecycle, and build-selected strategies; adapters in `App.tsx` derive resolver state from the backing while preserving the locked Canvas header behavior.
- Implemented P30b Phase 2: `apps/desktop/src/canvasTargeting.ts` defines `ElementRef`, bounds, and `TargetResolution` confidence rules, plus a hidden preview metadata collection script for `data-canvas-id`, optional source file, and component metadata. This target metadata remains support data for future patches/conversion/Edit Mode and is not rendered in Canvas chrome.
- Implemented P30b Phase 3: `visualPatchRuntime.ts` now supports preview-only `VisualPatch` V1 bundles with `style`, `text`, `hide`, and `show` operations, named bundle apply/clear, idempotent reapply after DOM replacement, and source-safe restoration. This remains hidden preview runtime plumbing only; it does not add Canvas header UI, hot-swap lane switching, source conversion, or P31 Edit Mode.
- Implemented P30b Phase 4: live proposal variants can carry hidden `visualPatchBundle` metadata. `planPreview.ts` and `localState.ts` validate persisted bundles, and `LiveAppPreview` applies or clears them on the existing webview when switching `Live` and proposal lanes. Normal swaps avoid reloads and preserve guest state; failed patch-backed selection reloads only the current preview as fallback. No Canvas header UI, source conversion, or Edit Mode behavior is added.
- Implemented P30b Phase 5: `apps/desktop/src/canvasVisualReferences.ts` turns validated VisualPatch target metadata into hidden `Change N` proposal highlights, and `LiveAppPreview` merges those with authored highlights for the existing `Changes` overlay. Adjusted change areas are stored as composer Visual References with thread/proposal/option/lane/route/viewport/screenshot/bounds/source metadata for prompts; visible chip labels remain compact.
- Implemented P30b Phase 6: `Build selected` on `live_dom_patch` proposals routes to a normal agent implementation turn with `convert_dom_patch_to_code` guidance, accepted VisualPatch bundle metadata, source/component hints, and convention-preserving rules. The desktop marks the proposal `accepted_for_build` and removes it from active routing while keeping it visible as a reference; code-backed proposals still use `promote_code_workspace`.
- Implemented P30b Phase 7: `apps/desktop/src/canvasProposalStaleness.ts` evaluates proposal staleness separately from display lane labels. Live DOM patch proposals require a stored VisualPatch bundle, matching project/preview URL/route/viewport, resolvable `data-canvas-id` targets, and matching source hints before patch apply or `Build selected`; stale proposals surface refresh/rebase/archive/open-live recovery language and are not silently applied. Code-backed workspace proposals also require a backing workspace path before build.
- Implemented P30b Phase 8: desktop Plan Mode sends `turn/start.planningOnly`, and Rust/app-server clamps the turn to approval `never` plus a managed permission profile that reads the project but writes only app-managed review artifacts under `.codex/mockups`. The turn also forces the managed sandbox level so patch/tool writes remain enforceable; legacy sandbox/profile overrides cannot widen a planning-only turn.
- Implemented P30b Phase 9: code-backed proposal workspaces now persist through the app-owned proposal registry in `apps/desktop/electron/proposal-workspaces.cjs`. The registry is stored under the Electron `proposal-workspaces/registry.json` cache, records project-hashed workspace roots, `registryId`, option `previewOwnerId`, and option workspace paths, and validates registry bounds before diff/apply. React local state remains the presentation cache for active/compare lanes, not the sole source of source-affecting proposal truth.
- Shelved P31/P32 architecture: Canvas direct-manipulation edit sessions and move-only generated-DOM addressability are not the current product path. Keep existing historical design notes only as fallback context; do not build new general DOM editor, proxy movement, or move-intent infrastructure ahead of P33.
- Agent-authored `Change N` marks and user-authored visual references may still be useful evidence for draft revision, but P33 should route them as context for the active Live-first draft rather than making direct manipulation the main interaction.
- Planned P27-agent-aware architecture: derive a compact Canvas lane awareness payload from the same resolver/lane adapter state used by the preview surfaces. Prompt/routing context should tell the agent the selected lane, Live status, proposal backing kind, active-versus-history lifecycle, viewport, marks/changes, and build meaning without exposing internal paths. P29 Browser Observer/Actor should later consume this lane state for inspection, but it should not own the baseline prompt-awareness work.

## Plan Mode

- Plan Mode is an implementation gate: no app implementation file changes until the user accepts.
- Plan proposals store project/thread/turn identity, the original prompt, attached App/Mockup mark contexts, optional live preview metadata, status, kind, and timestamps.
- P28 direction: visual plans should pin Visual References, not just current mark context. A Visual Reference should preserve the backing project/thread/proposal/option/route/viewport/screenshot/bounds/note/source metadata needed to implement the visual story later.
- Plan acceptance starts a normal implementation turn. It may include selected preview or mark context as guidance, but it does not save visual review artifacts as durable project memory.
- Plan revision sends typed feedback plus any selected preview or mark context. Revision stays in Plan Mode and should remain product-facing.
- Plan Mode may create review-only `.codex/mockups` artifacts when visual review is itself the plan. The app-server prepares that artifact directory and permits writes there while keeping implementation files read-only until explicit acceptance.
- When a Plan Mode review artifact is accepted through `Build selected`, the desktop stages editable implementation text and clears Plan Mode for that project so the next send is an implementation turn with selected option, route, viewport, and mark context as hidden support.

## Prompt Wrappers

- Prompt wrappers must preserve the visible user request in chat/sidebar titles. Internal sentinels and control payloads should not appear as user text.
- Empty-project visual-option prompting is LLM-led: the desktop may attach compact project state and capability guidance, while the agent decides whether to ask a Canvas question, save proposals first, or implement directly.
- Empty-project visual-option prompting should be routed only for broad UI/app/product creation or explicit preview-option requests. Operational command/script/no-edit prompts use the normal turn path even when the folder is empty.
- Existing-app broad UX/UI prompts use the same Canvas question wrapper and decision-strip protocol when clarification is needed; the agent authors the wording from the request.
- Existing-app preview-first prompts route by specificity: small control/placement/menu/panel proposals prefer temporary Live overlay proposals; explicit wireframes/mockups, broad visual exploration, Live-unavailable cases, and complex structural changes use saved `.codex/mockups` fallback. Ambiguous exploratory visual follow-ups use the current-app decision strip before artifacts or overlays are generated; the agent authors the strip content while the desktop provides allowed `canvasAction` routing values and product constraints.
- Canvas-relevant prompt wrappers should include current lane awareness when available: selected `Live/A/B/C`, backing kind, lifecycle, route, viewport, and attached visual references. The wrapper should stay compact and factual; it must not leak proposal workspace paths, hidden JSON payloads, or desktop-only IDs into visible chat.
- P25b routing splits that fallback further: empty-project visual options and explicit serious runnable existing-app preview requests prefer code-backed proposal workspaces, while explicit rough wireframes/mockups and Live-unavailable fallbacks remain saved `.codex/mockups`.
- Decision-only prompt wrappers may mention `.codex/mockups` output rules, but completion handling must not treat them as artifact-creation turns. Only turns that actually request review artifacts should activate a current proposal set or auto-open Mockup Preview.
- App/Mockup mark contexts serialize only the relevant project, preview/mockup identity, viewport, marked rectangle, note, timestamp, and optional renderer-owned thumbnail data URL for display. They are temporary communication context, not DOM selectors.
- Existing-app visual-decision sends preserve project-scoped App/Mockup mark contexts through the selected choice so a user's marked location still supports the eventual preview, revision, or implementation turn.

## Decision Strips

- Empty-project visual planning can start with a `codex-decision-strip` fenced JSON block in the assistant response. The desktop strips that block from chat text and renders its choices above the composer.
- Decision-strip/control JSON is never user-facing chat content. Strip complete and partially streamed decision payloads before rendering assistant text, while preserving normal progress/thinking UI.
- P27-cool direction: decision strips should become the single questionnaire surface for Canvas proposal choices. The renderer should support 2-3 choices per row, short labels, and an optional second row for fidelity choices, while preserving hidden routing metadata for direct build, one proposal lane, or A/B/C proposal lanes.
- Visual-decision, mockup revise/add/build, and selected-option sends must continue the active thread when one exists. Draft project routing is only for a truly new chat, not for actions inside an existing thread.
- Thread refresh must preserve active local drafts and pending sends. If a project has no valid active or last-active thread, the desktop should leave `activeThreadId` empty instead of falling back to the newest server thread.

## Mockup Preview

- Saved mockups live under the project folder in `.codex/mockups/manifest.json` and up to three HTML files such as `mockup-a.html`, `mockup-b.html`, and `mockup-c.html`.
- Saved mockups are concept artifacts. They can be reopened, switched, revised, added to, marked, or built from, but they are not localhost apps or code branches.
- Code-backed proposal workspaces are the branch-like lane for promotable runnable options. Do not overload saved mockups with branch semantics.
- Code-backed workspaces must be resolved through the proposal registry before diff/apply. A workspace path by itself is not enough authority to build Live; it must belong to the registered project-hashed set root and selected option. Option preview ids own remembered preview URLs so proposal URLs do not leak into Live or other options.
- When saved `.codex/mockups` artifacts exist and the set is still an active decision, the desktop can render a compact A/B/C selector above the composer so users can open and switch the selected mockup without digging through Activity.
- The above-composer saved-mockup strip is only a selector. Heavier actions such as revise, add, and build belong to Mockup Preview and should stage the composer rather than send immediately.
- Build-selected sends must preserve two separate payloads: the visible user request for chat/title/display and hidden selected-mockup context for agent guidance. The visible request is authoritative and should override selected mockup context when they conflict.
- Build-selected staging stores visible prompt metadata on the submission draft. Chat, Activity, sidebar, and transcript display read that visible request or scrub the generic attached-context marker instead of rendering selected-option or mark payloads.
- Mockup Preview area marks are composer context (`@MockupMark`) with selected option, saved file, viewport size, named rectangle, timestamp, and optional thumbnail presentation metadata.
- Mockup mark rectangles are rendered from composer contexts. Removing the composer chip removes the matching rectangle, and saved rectangles are non-interactive so they do not block iframe clicks.
- Composer preview contexts are project-scoped. Project switches, new-folder selection, new chats, and prompt serialization must not show or send App/Mockup chips whose `projectId` differs from the active project. Sent composer contexts are retained only as desktop transcript presentation state so their picture chips can render above the matching user message.
- Saved mockup decisions are additionally thread-owned. The desktop may keep project-level `.codex/mockups` artifacts open in Inspector, but composer A/B/C selectors and hidden saved-mockup review context should serialize only when the owning thread is active.
- After a `Build selected mockup` turn starts, desktop records that project as mockup history mode. History mode hides the composer selector and commit actions while keeping saved mockups openable and markable as reference pages.
- Starting mockups that entered history mode must not be reused as active existing-app proposal tabs. New Live-plus-proposal comparisons require a fresh current-request review artifact set based on the live app; after P27-cool, single-proposal comparisons should use proposal lane `A`, not a separate `Preview` identity.
- Follow-up prompt routing must not target saved mockup history for normal feature requests. If the user asks for a new setting, page, placement, or option after building a mockup, prompt wrappers should route from current Live state and create fresh proposals rather than update the old saved Option A/B/C artifact.
- Saved mockup manifest entries may include proposal highlight rectangles with labels and notes. Electron normalizes bounds before exposing them; the renderer shows them as temporary proposal overlays, and adjusted highlights serialize as supporting composer context rather than accepted app chrome.
- Build-selected agent turns should create runnable files and clear start instructions, but should not launch preview/server processes. Electron's managed App Preview lifecycle owns project server start/stop after implementation.

## Desktop Shell

- On Windows, the Electron desktop shell starts a native Codex app-server sidecar plus a Windows-local origin-stripping bridge. User-facing project paths may stay Windows-style, but app-server calls must receive runtime-normalized paths.
- The WSL/Node bridge remains a dev runtime option only. A shareable build should follow the packaged Codex shape: ship a native app-server sidecar and launch it hidden from Electron, without requiring WSL, Node, or repo-local scripts on the recipient machine.
- The desktop shell selects the backend runtime by `P03_DESKTOP_BACKEND`: `real-native`/`native`/`sidecar` use the native sidecar, and `real-wsl`/`wsl` use the dev WSL helper. Electron defaults to the native sidecar.
- The native sidecar lane launches packaged `codex.exe app-server --listen ws://127.0.0.1:48889` and exposes the UI-facing bridge on `ws://127.0.0.1:48890`. Desktop dogfood/tests may override these with `CODEX_DESKTOP_APP_SERVER_PORT` and `CODEX_DESKTOP_BRIDGE_PORT` so a test Electron app does not collide with the running Codex Local app.
- Browser/WebView clients must not connect directly to app-server websocket. Electron owns the local origin-stripping TCP bridge so app-server can keep rejecting browser `Origin` headers while the desktop UI can connect through loopback.
- Dev helper processes receive `P03_DESKTOP_PARENT_PID` or are owned by the Electron process so rebuilds or forced closes do not leave orphan app-server helpers.
- Release desktop builds should not open a console window. Electron starts helper processes with no-window flags and keeps app-server logs in files rather than foreground terminals.
- `scripts/stage-desktop-sidecar.mjs` builds and stages the Windows release sidecar in `apps/desktop/electron/resources/codex-sidecar`: `codex.exe`, `codex-resources/codex-command-runner.exe`, `codex-resources/codex-windows-sandbox-setup.exe`, and `codex-resources/rg.exe`.
- Thread list/read/resume behavior must reconcile sidebar state and hydrated turns without showing stale chats or raw thread IDs.
- Electron exposes small native bridges for file/folder picking, image previews, auth URL opening, and preview/browser control; document ingestion remains an app-server/tool concern.
- Composer image attachments use Electron's file-path bridge plus app-server `localImage` inputs. The desktop only renders chips/thumbnails and passes local paths; core owns converting those images for the model request. Preview mark thumbnails are display metadata on composer contexts and do not turn marks into model image attachments unless the user separately attaches an image.
- App Preview URLs are project-scoped. Electron keys managed preview processes by normalized project path and rejects probe/open requests for URLs owned by another managed project. The renderer also treats duplicate remembered localhost URLs across projects as stale unless the active project currently owns that managed preview, so old `127.0.0.1:5173` memory cannot make every folder show the same app.
- Electron must preserve the existing app-server boundary and local bridge semantics unless the app-server contract explicitly changes.
- Account/auth/model/usage visibility should come from app-server APIs. The desktop can start app-server `account/login/start` flows for ChatGPT browser auth, ChatGPT device-code auth, or API-key auth, then listen for `account/login/completed` and `account/updated`; it must not store or display tokens.

## Verification

- Parser/state logic should use unit-style checks where possible.
- React rendering behavior can use a browser/component harness.
- Repeated desktop flows should prefer DOM/state automation gates in the real desktop shell when available.
- Screenshots and manual pointer driving are useful for final visual sanity, but should not be the only repeated assertion layer.
- P33 manual gates should verify draft-workspace state through DOM/state checks, source hashes before/after `Build this`, draft brief creation/update, no hidden implementation leaks, and real Electron preview behavior across both interface-heavy and backend/workflow-heavy projects.
- After user-visible App Preview, Mockup Preview, Plan Mode, composer, or project behavior changes, dogfood in two local projects when feasible and say exactly what could not be verified.
