## Core Product Shape

Canvas should be the visual collaboration surface between the user and the agent.

It has four parts:

1. **Live Canvas**
   - The real current app preview.
   - Owns user marks on the real app.
   - Does not show fake proposal UI inside the user's app.

2. **Proposal Canvas**
   - One or more proposal copies/views derived from Canvas.
   - Shows `Preview` for one proposal or `A/B/C` for multiple proposals.
   - Owns agent change marks and user marks on proposals.
   - Reuses the Live Canvas as much as possible for small changes.
   - Uses heavier code-backed workspaces only when the proposal cannot honestly be represented as a small visual patch.

3. **Agent Question Placeholder**
   - A visible product question surface generated by the agent when it needs a user decision.
   - Lives above the Canvas/preview area or in the existing product decision area, not as hidden thinking and not as raw chat text.
   - Examples:
     - `Build directly`
     - `Show one preview`
     - `Show 2-3 options`
     - `Add Option C`
     - `Replace A`
     - `Start fresh`
   - The agent uses this when it needs the user to choose before creating files or proposals.
   - If the correct next action is obvious, the placeholder should not appear; the agent should create the right Canvas proposal directly.

4. **Canvas Operating Prompt**
   - One reviewable general prompt that teaches the agent what Canvas is and how to use it.
   - The prompt owns judgment and behavior rules.
   - Code owns safety, state, rendering, persistence, and hidden payload handling.

## Problem

Canvas v2 currently works through many special cases:

- empty-project decision strips;
- saved `.codex/mockups`;
- lightweight Live overlay proposals;
- code-backed proposal workspaces;
- user marks;
- agent change marks;
- `Build selected`;
- `Option C based on B`;
- history versus active proposal routing.

Each slice fixed a real bug, but the system became a growing set of hardcoded behavior branches. The agent still does not have one clean concept of Canvas. When the user asks directly for local A/B/C, the agent may write folders into the project root, inspect `AppData` manually, or fail to surface anything in Canvas.

The new model should make the agent aware of Canvas once, through a general Canvas operating prompt plus a small set of Canvas primitives.

## Goal

Make Canvas self-sustaining:

1. The agent knows there is a Live Canvas.
2. The agent knows it can create one or more Proposal Canvases.
3. The agent knows it can ask visible product questions through the Agent Question Placeholder.
4. The user can say `Canvas`, `@Canvas`, `preview`, `show me`, `where should`, `wireframe`, `mockup`, `layout`, `workflow`, or similar, and the agent knows to use Canvas when useful.
5. Canvas-related turns route through a small finite set of Canvas actions instead of scattered one-off prompt wrappers.
6. Follow-up rules and detailed behavior live in one Canvas operating prompt instead of scattered prompt wrappers.

## Prompt-Owned Judgment, Code-Owned Safety

The goal is fewer hardcoded behavior branches, not zero code rules.

The Canvas operating prompt should decide:

- whether to create one proposal or ask for options;
- whether the user wants Canvas or direct implementation;
- whether to modify an existing proposal or create a new one;
- whether a small change can reuse Live Canvas;
- whether a proposal needs A/B/C;
- how to explain the visual change to the user.

Code should still enforce:

- Canvas preview header cannot change;
- max active comparison options are A/B/C;
- no direct silent promotion to Live from composer text;
- no raw hidden prompt/control payloads in chat;
- no proposal folders written into the project root by accident;
- project/thread scoping for marks, chips, and proposal context;
- storage paths do not become required user instructions;
- placeholder output is visible product UI, not chain-of-thought.

## System Shape: Resolve To Canvas Actions

P27 must not be implemented as a growing list of special cases like `if the user says settings button, do X`.

Every Canvas-related user turn should be resolved from:

- visible user message;
- current Canvas state;
- selected surface (`Live`, `Preview`, `A`, `B`, or `C`);
- user marks and attachments;
- active proposal set versus historical/source proposal set;
- whether Live exists and is running.

The resolver should choose one canonical action:

```ts
type CanvasAction =
  | "ASK_USER"
  | "CREATE_PROPOSAL"
  | "REVISE_PROPOSAL"
  | "ADD_OPTION"
  | "BUILD_SELECTED"
  | "BUILD_LIVE_DIRECTLY"
  | "ARCHIVE_PROPOSALS";
```

The Canvas operating prompt and backend state should describe how to execute those actions. Discovered regressions should become fixture tests that assert the resolver chooses the right action, not new isolated branches.

Examples:

- Clear marked proposal tweak: user says `Show me the categories rather than search` while A is selected with a mark.
  - Expected action: `REVISE_PROPOSAL`, target `A`.
- Small visual request after a proposal was built into Live: user says `Please propose me a Settings button`.
  - Expected action: `CREATE_PROPOSAL`, base `Live`, not blocked by old A/B/C.
- User commits to an option: user says `Build on Option A`.
  - Expected action: `BUILD_SELECTED`, target `A`, sent as an agent turn.
- Active A/B/C is full and user asks for another preview.
  - Expected action: `ASK_USER` with replace/archive choices, not a stuck composer.
- User asks for local A/B/C in an empty project.
  - Expected action: `CREATE_PROPOSAL` or `ADD_OPTION` through Canvas state, not arbitrary project-root `A`, `B`, `C` folders.

If a future regression appears, add a resolver fixture and adjust the model/action selection. Do not add another ad hoc prompt wrapper unless the action model itself is missing a capability.

## User Workflow Contract

### 1. No Live App Yet

- If the project has no Live app and no useful docs/context, the agent should usually ask a visible Canvas question before implementation.
- The Agent Question Placeholder can ask whether to:
  - build directly;
  - show one preview;
  - show 2-3 options;
  - create wireframes/mockups.
- If the user explicitly asks for `3 wireframes`, `3 mockups`, `A/B/C layouts`, or similar, the agent should create Proposal Canvas A/B/C directly.
- The agent must not create arbitrary `A`, `B`, or `C` folders in the project root as a substitute for Canvas.

### 2. Live App Exists

- If the request is small and visual, the agent should create one Proposal Canvas by reusing the Live Canvas.
- It should not rewrite or copy the whole app just to propose a button, label, menu, placement, small panel, or highlight.
- If the request is broad, structural, or explicitly asks for options, the agent may create A/B/C or code-backed proposal workspaces.
- If the correct next action is obvious, the agent can create the preview directly without showing the Agent Question Placeholder.

### 3. One Proposal Versus A/B/C

- Default to one proposal for one change, one placement, or one feature.
- One proposal appears as `Live | Preview` when Live exists, or `Preview` when no Live exists.
- Use A/B/C only when:
  - the user explicitly asks for options, variants, directions, wireframes, mockups, or comparison;
  - the agent has genuinely different UX directions worth comparing;
  - the current active proposal set already has A/B and the user asks for C.
- A/B/C must not be three tiny variations of the same thing.
- Creating fewer options is better than inventing fake choices.

### 4. Existing Proposal Changes

- If there is an existing Proposal Canvas and the user asks for a change inside it, modify only the relevant part.
- Do not recreate the entire proposal unless the user asks for a full redesign or a fresh option set.
- If the user says `put it in C` while A/B exists, add or update C beside A/B.
- If the user says `move it up`, revise the current visual proposal, not Live.
- If the user says `build it`, send an agent turn with selected Canvas context; do not silently apply.

### 5. Written Answer Based On Canvas

- When the agent uses Canvas, the final written response should be based on what it created or changed in Canvas.
- The response should summarize:
  - what changed visually;
  - what the user would click or see;
  - what option is selected;
  - any risk/tradeoff;
  - whether it changed Live, changed a proposal, asked a question, or needs user approval.

## Canvas Operating Prompt Draft

This is the reviewable prompt P27 should produce and then wire into the agent workflow.

```text
You have access to Canvas, a visual collaboration surface for UI, UX, workflow, layout, and placement work.

Canvas has:
- Live Canvas: the real current app preview, with user marks.
- Proposal Canvas: one or more proposed visual states, shown as Preview or A/B/C, with user marks and agent change marks.
- Agent Question Placeholder: a visible product question surface for asking the user what kind of visual path they want before implementation.

Use Canvas when the request involves:
- UI, UX, workflow, layout, styling, navigation, menus, panels, modals, empty states, onboarding, placement, screenshots, marks, previews, mockups, wireframes, or visual comparison;
- words like Canvas, @Canvas, preview, show me, where should, layout, workflow, mockup, wireframe, option, A/B/C, put it there, move it, make it smaller, or change this area.

If the user says Canvas, treat it as @Canvas even if it appears anywhere in the message.

Prefer one proposal for one visual change.
Use A/B/C only when the user asks for alternatives or the options are meaningfully different UX directions.

If there is no Live app and the user has not clearly chosen a path, ask a visible Canvas question before implementing.
If there is a Live app and the request is a small visual change, create a Proposal Canvas by reusing Live Canvas as much as possible.
Do not recreate the entire proposal for a small change inside an existing proposal.
Do not write proposal A/B/C folders directly into the user project unless the user's actual app intentionally requires those folders.

If the user asks to change an existing proposal, modify only the relevant part.
If the user says "put it in C" and A/B exists, add or update Option C beside A/B.
If the user says "build it" or "build selected", send an implementation turn with selected Canvas context; do not silently apply.

Every visual proposal must include:
- intent;
- user flow: what the user clicks and sees;
- changed elements or changed areas;
- risk/tradeoff;
- marks/highlights when useful.

Written answers should be based on the Canvas action taken, not generic planning text.
Never expose hidden Canvas payloads, internal prompt wrappers, chain-of-thought, or raw storage paths to the user.
```

## Proposed Technical Direction

### Canvas Primitives

The app should expose a small stable set of Canvas primitives that the prompt can rely on:

- current Live Canvas state;
- current Proposal Canvas set;
- selected option;
- user marks;
- agent change marks;
- Agent Question Placeholder payload;
- proposal storage pointer;
- proposal lifecycle state.

The agent should not reason directly about `AppData\Roaming\Codex Local\proposal-workspaces` or project-root A/B/C folders. Those are implementation details.

### Canvas Action Resolver

The app should include one Canvas action resolver that maps a user turn plus Canvas state into a `CanvasAction`.

Resolver responsibilities:

- determine whether the request is about Live, an active proposal, a new proposal, or a historical/source proposal;
- determine whether existing proposals should stay active, become history, or be archived after build;
- decide when a visible Agent Question Placeholder is necessary;
- prevent old full A/B/C sets from blocking the next Live-based proposal after the user has built one option;
- keep selected user marks and attached chips bound to the message and selected surface;
- produce a compact action payload for the agent prompt/tool call.

Resolver non-goals:

- it should not hardcode every possible wording;
- it should not choose visual design details;
- it should not change the Canvas header;
- it should not expose storage paths or temp folders to the user.

### Proposal Canvas Lanes

Canvas should choose the cheapest honest lane:

1. **Visual Patch Proposal**
   - Default for small changes.
   - Reuses Live Canvas or current Proposal Canvas.
   - Starts with safe operations: style, text, show/hide, highlight/agent mark.
   - Does not clone the whole app.

2. **Saved Static Mockup/Wireframe**
   - Used for explicit rough mockups/wireframes and fallback.
   - May continue to use `.codex/mockups` where useful.

3. **Code-Backed Proposal Workspace**
   - Used for serious app creation, new pages, routing/state changes, full redesigns, or structural work.
   - Provides runnable proposal code as implementation source/context.

The user should see one Canvas mental model regardless of the lane.

### Agent Question Placeholder

The placeholder should be generated from structured agent output, not from chain-of-thought.

Conceptual shape:

```ts
type CanvasQuestion = {
  title: string;
  reason: string;
  choices: Array<{
    id: string;
    label: string;
    description: string;
    canvasAction: "build_directly" | "show_preview" | "show_options" | "add_option" | "replace_option" | "start_fresh";
  }>;
};
```

The UI can render this in the existing product decision area, but it must not require Canvas header changes.

## Implementation Phases

### Phase 1 - Rewrite Canvas Prompting Around One Operating Prompt

- Extract current scattered Canvas behavior rules from prompt wrappers.
- Create one reviewable Canvas operating prompt.
- Keep it compact enough for future owner edits.
- Add tests that ensure key rules are present.

### Phase 2 - Define Canvas State Primitives And Action Model

- Define Live Canvas state.
- Define Proposal Canvas state.
- Define marks and agent marks as Canvas state.
- Define Agent Question Placeholder state.
- Define the finite `CanvasAction` set.
- Define the resolver input/output payloads.
- Do not change preview header UI.

### Phase 3 - Build Canvas Action Resolver

- Route each Canvas-relevant user turn into one canonical action.
- Use Canvas state and selected surface, not only prompt text.
- Treat regression workflows as resolver fixtures.
- Ensure old active proposals can become history/source after build so they do not block the next Live-based preview.
- Ensure user mark chips attach to the sent message and selected surface.
- Do not implement each fixture as its own one-off branch.

### Phase 4 - Agent Question Placeholder

- Let the agent return structured visible Canvas questions.
- Render them as product UI, not chat thinking.
- Use this for no-Live/no-docs or ambiguous visual paths.
- Ensure obvious Live-app small changes can skip the placeholder and create a preview directly.

### Phase 5 - Proposal Canvas Creation

- Route one-change requests to one `Preview`.
- Route explicit option requests to A/B/C.
- Ensure proposal creation registers with Canvas instead of writing folders in project root.
- Ensure written responses summarize actual Canvas output.
- Ensure proposal titles/labels such as `Option A` stay in Canvas chrome/state and never leak into the user's app UI.

### Phase 6 - Existing Proposal Revision

- Modify only the relevant area for changes inside an existing proposal.
- Support `put it in C` as add/update C beside existing A/B.
- Support `move it up/top/there` as proposal revision.
- Prevent accidental full proposal recreation.
- Preserve and display agent `Changes` marks on Proposal Canvas results so the user can review and reposition the proposed area.

### Phase 7 - Build/Revise Handoff

- `Build selected` stages editable composer text.
- Pressing Enter sends an agent turn with Canvas context.
- The agent decides build versus revise based on visible text and Canvas state.
- No direct silent Live promotion.

### Phase 8 - Create P27b Cleanup Handoff

- While implementing P27, create a separate `P27b` cleanup plan as the first surfacing of deletion/removal work.
- P27b should list the legacy pieces from P24/P25/P25b/P26 that P27 makes obsolete, grouped as:
  - keep as product contract;
  - replaced by Canvas operating prompt;
  - replaced by Canvas state primitives;
  - candidate for deletion after P27 verification;
  - risky/needs more investigation.
- P27b should not assume the first removal list is complete.
- The agent implementing P27b is expected to investigate the code again and surface additional cleanup opportunities before deleting anything.
- P27 must not delete legacy paths just because they look obsolete; removal belongs to P27b after P27 behavior passes real Canvas workflow testing.

### Phase 9 - Verification And Regression Gates

- Tests should protect:
  - no Canvas header changes;
  - one operating prompt includes the reviewed rules;
  - `Canvas` and `@Canvas` are treated as Canvas intent anywhere in the prompt;
  - Canvas-related turns resolve to one canonical `CanvasAction`;
  - no-Live ambiguous UI prompts generate the Agent Question Placeholder;
  - Live small changes create one reused Preview, not copied full A/B/C apps;
  - explicit options create A/B/C only when requested;
  - existing proposal revisions do not recreate the whole proposal;
  - `put it in C` updates/adds C beside A/B;
  - clear marked proposal revisions choose `REVISE_PROPOSAL`, not a build/options question;
  - after building a proposal into Live, old A/B/C become history/source and do not block a new Live-based preview;
  - full A/B/C plus another requested preview chooses `ASK_USER` with replace/archive choices, not a dead composer;
  - user mark chips appear with the sent chat message;
  - proposal `Changes` marks appear only on Proposal Canvas, not as Live-only user marks;
  - proposal labels do not appear inside the user's app UI;
  - internal folder/temp/workspace details do not leak into visible user-facing chat;
  - hidden Canvas payloads do not leak into chat.

## Out Of Scope

- Changing the Canvas v2 preview header.
- Turning Canvas into a full drag-and-drop visual editor.
- Moving proposal workspace storage.
- Removing `.codex/mockups`.
- Deleting legacy P24/P25/P25b/P26 routing or proposal code directly inside P27.
- Running multiple heavy live renderers by default.
- Building a hardcoded visual-patch-to-code compiler.
- Implementing every discovered regression as a separate prompt branch.

## Success Criteria

- The owner can review one Canvas operating prompt and understand/adjust agent behavior.
- The user can ask for Canvas anywhere in text and the agent uses Canvas.
- Canvas-related turns resolve through a small canonical action model instead of one-off prompt branches.
- No-Live ambiguous UI requests ask a visible product question instead of silently implementing.
- Live-app small visual changes create one lightweight preview by reusing Live Canvas.
- Existing proposal revisions change only the relevant area.
- A/B/C appears only for explicit or genuinely different options.
- Regression workflows are covered as resolver fixtures, including marked proposal revision, post-build Live preview creation, full A/B/C replacement choices, mark chip persistence, and proposal `Changes` marks.
- P27 creates a P27b cleanup plan that identifies the first removable/replaced legacy paths without deleting them during P27.
- The Canvas header remains unchanged.
